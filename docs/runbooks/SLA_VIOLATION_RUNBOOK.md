# AssetForge SLA Violation & Incident Runbook

This runbook outlines standard operating procedures (SOPs) for responding to alerts generated by `monitoring/alerts.yml` when platform SLAs or SLOs are threatened or breached.

---

## 1. Availability Error Budget Burn (`SLOAvailabilityErrorBudgetBurningFast` / `Slow`)

### Symptoms
- 5xx status codes exceeding 1% (fast burn) or 0.1% (slow burn).
- PagerDuty notification triggered.

### Immediate Triage Steps
1. **Identify Failing Endpoints**:
   ```promql
   sum(rate(http_requests_total{status=~"5.."}[5m])) by (endpoint, status)
   ```
2. **Inspect Application Pod Logs**:
   ```bash
   kubectl logs -n production -l app=kor-assetforge --tail=100 | grep -i "error"
   ```
3. **Check Database Health**:
   - Inspect PostgreSQL connection pool metrics: `db_pool_in_use_connections`.
   - Verify if slow queries or deadlocks are causing request timeouts.
4. **Evaluate Recent Deployments**:
   - If a deployment occurred in the last 15 minutes, prepare immediate rollback:
     ```bash
     kubectl rollout undo deployment/kor-assetforge -n production
     ```

---

## 2. p99 Latency Breach (`SLOLatencyP99Breached`)

### Symptoms
- 99th percentile latency on critical endpoints exceeds 500ms for > 3 minutes.

### Immediate Triage Steps
1. **Locate High-Latency Routes**:
   ```promql
   histogram_quantile(0.99, sum(rate(http_request_duration_seconds_bucket[5m])) by (le, endpoint))
   ```
2. **Check Cache Status**:
   - Check if Redis circuit breaker is open: `cache_redis_circuit_breaker_state == 2`.
   - If circuit is open, database may be receiving 100% of read traffic without caching.
3. **Execute Emergency Cache Warming**:
   - If cold-start cache misses are overwhelming the database, trigger warming:
     ```bash
     ./scripts/warm_cache.sh --concurrency 8 --target assets
     ```
4. **Database Indexing & Locks**:
   - Check for unindexed table scans or lock contention in PostgreSQL.

## 3. Redis Circuit Breaker Open (`RedisCircuitBreakerOpen`)

### Symptoms
- Alert fires indicating Redis circuit breaker is `OPEN` (state=2).
- Traffic is degrading gracefully to PostgreSQL with `X-Cache-Degraded: true` header.

### Immediate Triage Steps
1. **Check Redis Connectivity**:
   ```bash
   redis-cli -u "$REDIS_URL" ping
   ```
2. **Review Redis CPU / Memory**:
   - Check memory exhaustion or eviction storms in Redis.
   - If Redis restarted or OOM killed, verify persistent storage and cluster state.
3. **Circuit Recovery**:
   - The circuit breaker will automatically enter `HALF_OPEN` after 30 seconds and test downstream connectivity.
   - Once Redis stabilizes, consecutive successful requests automatically close the circuit.
   - If manual reset is required: restart the application pods with rolling restart.

---

## 4. In-Memory L1 Cache Pressure (`L1CacheMemoryPressure`)

### Symptoms
- L1 cache memory utilization exceeds 90% of configured maximum (`CACHE_L1_MAX_SIZE_MB`).

### Immediate Triage Steps
1. **Inspect L1 Eviction Metrics**:
   - Verify that LRU evictions are occurring as expected.
2. **Identify Memory Hogging Keys**:
   - Look for oversized JSON payloads or large query results being cached in L1.
3. **Adjust Sizing**:
   - If host memory allows, increase `CACHE_L1_MAX_SIZE_MB` via pod environment configuration.
